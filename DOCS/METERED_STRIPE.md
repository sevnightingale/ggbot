Implementing Metered Billing for LLM Token Usage (Stripe)
Technical Implementation: Metered Token Billing with Stripe
Measuring and Tracking Token Consumption: Start by instrumenting your application to count tokens for each user’s LLM requests. If you’re using a third-party LLM API (e.g. OpenAI), leverage its response metadata (such as the usage field) to get the number of input and output tokens consumed. Record these usage counts in your database tied to each customer, so you have an authoritative log of how many tokens each user has used in the current billing period. This usage logging is critical both for billing and for showing users their consumption. Integrating with Stripe Usage Records: Stripe supports usage-based (metered) billing, meaning you can charge customers based on the token counts you record
docs.stripe.com
. In Stripe’s “classic” usage-based model, you create a product price with recurring.usage_type = metered and a unit cost per token (or per block of tokens). For example, you might set a price of $0.0005 per token (or $0.50 per 1,000 tokens). Each subscription to that price will accumulate usage. You report the usage to Stripe by creating usage records on the subscription’s line item. Stripe then sums up all usage records in the billing period and automatically invoices the customer for the total tokens used

docs.stripe.com
. When sending usage records via the Stripe API, you typically provide the subscription item ID, a quantity of tokens, and a timestamp. You can decide how often to report usage – some implement “real-time” metering (report on every API call) while others batch updates (e.g. once per day or hour)

docs.stripe.com
. A common best practice is to batch usage to avoid hitting rate limits or incurring excessive API calls. For example, instead of recording one usage record per token, aggregate and send one usage record for every N tokens or for each API request’s total tokens
docs.stripe.com
. Stripe’s API can handle high volumes, but they note a rate limit of ~100 calls/sec (extendable to 200/sec on request) for usage reporting
docs.stripe.com
docs.stripe.com
. If your application could exceed this, bundle your usage updates – for instance, if you charge per token, consider reporting usage per 1,000 tokens as a single record (quantity = 1000) to reduce call frequency
docs.stripe.com
. Be sure to use idempotency keys when recording usage so that retrying a usage report (due to a network issue, etc.) doesn’t accidentally double-count
docs.stripe.com
. Stripe will total up all usage records (which by default are summed) for the period when generating the invoice.
🔧 Example: If a user prompts the LLM and uses 250 tokens, you might immediately send a usage record of 250 tokens to Stripe for that user’s subscription. If instead you batch daily, you’d accumulate that 250 in your database, and later create a usage record for the day’s total (say 1,000 tokens from multiple requests). In either case, Stripe will add these up for the monthly bill. Just ensure the timestamp you attach to each usage record falls within the current billing period (Stripe rejects usage with timestamps outside the current cycle)

Setting Up Stripe Subscription and Pricing: In Stripe, configure a metered billing price for your token usage. You may choose a straight per-token rate or define tiers. For instance, Stripe’s documentation illustrates a plan where the first 1,000 tokens in a month are free (unit price $0), and each token beyond that is billed at $0.04
docs.stripe.com
. To achieve this, you would create a product for “LLM API Usage” (for example) and then create a price with a metered usage type and tiered pricing. In the Stripe Dashboard you can specify tiers (e.g. 0–1000 tokens at $0, 1000+ tokens at $0.04 each)
docs.stripe.com
. Under the hood, this creates a price with tiers_mode=graduated and the two tiers as described
docs.stripe.com
docs.stripe.com
. Then, subscribe each customer to this price (often as part of a subscription plan). In many SaaS scenarios, you’ll pair a usage-based component with a base subscription fee. You can create multiple items on a Stripe subscription – for example, a fixed monthly base fee product and a usage-based product for tokens. The Stripe guide’s fictional “Hypernian” AI service does exactly this: it charges customers a flat $100/month license fee plus metered token fees beyond a threshold (0–1000 tokens free, then $0.04 per token)
docs.stripe.com
. In Stripe, that’s implemented as one subscription item for the $100 recurring fee and a second subscription item using a metered price for the tokens (with the free allotment built into the tiered pricing)
docs.stripe.com
. This approach (sometimes called a “fixed fee + overage” model) is very common for SaaS: customers get a predictable base service and you still capture revenue from heavy usage. If you prefer pure usage billing (no base fee), you can simply omit the fixed item and have the subscription consist of only the metered usage price – Stripe will then bill solely based on tokens consumed each period. Webhooks for Billing Automation: Implement Stripe webhooks to streamline the billing cycle for usage-based charges. Key webhooks include:
invoice.upcoming (fires a short time before a billing period ends and an invoice is created). You can use this as a cue to post any last-minute usage records for the ending period. For example, if your billing period ends at midnight on the 30th, Stripe might send an invoice.upcoming event a few hours prior – your handler can gather any usage not yet reported (e.g. tokens used that day) and send a final usage record so that it’s included on the upcoming invoice. This helps ensure all token consumption is accounted for on the bill.
invoice.created / invoice.finalized. Once the invoice is generated with the usage charges, you might want to notify the customer or record the amount. You could, for instance, email the user a summary of their token usage and charges. The invoice.finalized event indicates the invoice is ready to go (no more updates), and invoice.payment_succeeded / invoice.paid lets you know the payment went through. Use these to provision continued service or, if payment fails (invoice.payment_failed), to potentially pause the user’s access to the LLM features until they rectify their payment.
customer.subscription.updated events can inform you of changes like plan upgrades, cancellations, etc., which might affect how you handle usage. If a subscription is cancelled mid-period, for example, you might choose to immediately invoice for any accrued usage (Stripe by default will invoice at period end or at cancellation time for prorated amounts). Ensure your cancellation logic aligns with your usage billing – e.g. you might allow the user to use any remaining included tokens until the end of the period but not beyond if they’ve canceled.
Monitoring and Usage Limits: With usage-based models, it’s important to guard against runaway usage (both for customer bill shock and to protect your costs). Stripe Billing supports usage threshold alerts that you can configure per customer or per plan. For instance, you can set a rule like “notify me (or the customer) when this user’s usage in the month exceeds 100,000 tokens”
docs.stripe.com
. Such alerts can be delivered via webhook or email. You might use them to email the user (“You’ve used 100k tokens this month, 90% of your plan’s allotment”)
docs.stripe.com
. Additionally, Stripe allows billing thresholds that can automatically trigger an invoice when a certain usage cost is reached mid-cycle
docs.stripe.com
. For example, you could configure a monetary threshold so that if a customer’s usage charges hit, say, $500 before month-end, Stripe immediately finalizes an invoice at that point
docs.stripe.com
. This mechanism can protect you from a scenario where a customer incurs a huge amount of usage cost early in the month and then fails to pay at period end – by invoicing at a threshold, you collect in smaller increments. It also protects the customer by not letting an unmonitored service rack up an enormous bill unexpectedly. In your app logic, you might also enforce your own limits (e.g. maybe your free tier users are capped at 50k tokens total). In that case, when your internal counter hits 50k, you’d stop further LLM calls for that user or prompt them to upgrade their plan (this is the “deprovision access” scenario when a free limit is exceeded)
docs.stripe.com
. Finally, provide transparency to users about their usage. It’s highly recommended to show each user their token consumption in your app (e.g. a usage dashboard or even just a counter in their account settings) along with an estimate of how it translates to cost. This builds trust and helps users self-manage their usage. Stripe’s best-practice guidelines for usage-based SaaS echo this: give customers tools to monitor usage and understand their bill

. For example, you might show “You’ve used 75,000 tokens this month, 25,000 tokens remain before incurring overages” or “Estimated cost so far: $3.00”. Such transparency can reduce disputes and surprises when the invoice is issued.
Pricing Strategy for Usage-Based LLM Services
Designing a pricing strategy for an AI SaaS that resells LLM access requires balancing predictability for customers with coverage of your variable costs. Here are key considerations: Choosing a Pricing Model – Pay‑as‑you‑Go vs. Hybrid Plans: Decide whether to charge purely by usage or to offer a hybrid of subscription and usage. A pure pay-as-you-go model means customers pay solely based on tokens consumed, with no recurring base fee. The advantage is maximum fairness and transparency – users pay only for what they use, much like how AWS or Twilio charge for API calls

. This model guarantees your margins on each request (you’re always covering cost with revenue) and scales revenue automatically with usage

. However, purely usage-based billing can result in unpredictable bills for customers (and revenue variability for you)

. Many SaaS companies therefore adopt a hybrid pricing model: for example, a monthly base subscription that includes a certain token allowance, plus overage charges for extra usage

. This gives the customer some predictability (they know their base cost and the “free” usage included) while still letting you charge heavy users more. The Stripe guide example above (Hypernian) is exactly this: flat $100/month + usage overages beyond 1000 tokens
docs.stripe.com
. Another common approach is credit-based plans: the customer’s monthly fee converts into a bundle of credits (tokens) they can spend. For instance, an AI writing app might charge $50/month and include 1 million tokens as credits. If the user runs out, they can purchase additional credits or get more next cycle

. Credit systems are essentially usage-based, but by pre-packaging tokens into a subscription, they feel more like a plan than a meter. This approach (used by platforms like Relevance AI) avoids surprise bills and ensures a baseline revenue per user

. The downside is if credits and real usage don’t align well (confusion about “what does one credit get me?”)

. In practice, hybrid models – some included usage plus paid overages – are very popular for AI SaaS because they offer the “best of both”: predictable income and the ability to monetize high usage

. Setting a Price per Token (Cost plus Margin): Pricing tokens involves understanding your own cost and adding a sustainable margin

. Since you are effectively reselling an API (OpenAI or another LLM), you’ll be paying the provider per token. Calculate the effective cost (e.g., OpenAI’s GPT-4 might cost ~$0.03 per 1K input tokens and $0.06 per 1K output tokens, depending on the model

. For example, if using an OpenAI model that costs you $0.002 per 1,000 tokens, you might charge your customers $0.003 per 1,000 – a 50% markup to cover overhead, support, and profit. . Even if you’re not in that beta program, the principle holds: price tokens in a way that covers your costs plus a margin for your business. Also consider the variance in token costs: more powerful models (GPT-4, etc.) cost more per token than smaller models, and input vs output token rates can differ

. You have a few options to handle this: (a) Simplify by charging one blended rate for all tokens (perhaps weighted towards the higher-end cost). (b) Charge different rates for different models – e.g. tokens used on a “basic model” are cheaper than tokens on a “premium model.” Some SaaS products do this by offering tiers: a standard plan might only allow cheaper models, whereas a premium plan unlocks GPT-4 but at a higher usage cost. If you need granularity, Stripe’s advanced usage billing supports defining dimensions (like model = GPT4 vs GPT3) on usage records
docs.stripe.com
, but a simpler route is separate meter items or separate pricing for the expensive usage. The key is to ensure heavy use of an expensive model doesn’t erode your margin – either limit it to higher-paying customers or mark its cost up appropriately. Keep an eye on your provider’s pricing changes. AI API prices can change (sometimes downwards with scale, or upwards for new models). Your pricing model should be able to adapt. If OpenAI drops prices, you might pass savings to customers or maintain your price for more margin – but you’d want to know promptly. Conversely, if they raise prices, you’ll need to adjust your rates to avoid losing money. (This is where having a margin % approach is handy: you’d update token prices in your system or Stripe to maintain the margin.) Stripe’s LLM billing feature notifies if provider pricing changes
docs.stripe.com
, but otherwise make sure someone on your team monitors those announcements. Tiered Pricing and Overage Strategy: Decide if you will offer volume-based discounts or charge a flat rate per token regardless of volume. Tiered pricing can incentivize customers to use more. For example, you could charge $0.04 per 1K tokens for the first 1M tokens, $0.035 for the next 4M, and $0.03 beyond that (a volume discount for very high usage). Stripe supports this via graduated tier pricing – you’d define ranges and respective prices. Volume discounts make sense if your own costs per token decrease with scale or if you want to encourage large customers to commit to using your platform (instead of possibly going directly to the provider). If you do implement tiers, make sure they’re easy to understand. Often, it’s framed as “the more you use, the cheaper it gets.” This can be a selling point in enterprise sales. On the flip side, for smaller usage levels, you might have a minimum charge or base fee to ensure even low-volume customers contribute to your fixed costs. It’s also wise to include some free allowance either in a free trial or in each billing cycle for paid plans. A small included token bundle each month (say 10k tokens free) can act as a buffer so that trivial usage doesn’t nickel-and-dime the customer. It also helps with customer goodwill: they feel they’re not billed for every little action, only when they really start using the service heavily. As seen in the Hypernian example, the first 1,000 tokens were free as part of the base package
docs.stripe.com
. Many companies do similar “included” usage in plans. Just ensure the base fee covers the cost of that included usage on average – essentially the plan’s price should bake in the cost of the free tokens. Avoiding Bill Shock: One reason SaaS products sometimes shy away from pure metered billing is fear of bill shock – the customer uses the service heavily and gets an unexpectedly large invoice. To mitigate this, employ the strategies mentioned: clear usage visibility, alerts, and perhaps soft limits. For instance, you might by default cap usage at a certain amount unless the customer has a credit card on file and explicitly agrees to pay overages. Many SaaS with usage components will stop or warn at 100% of allotment, then require an upgrade or confirmation to continue. This can be a business decision based on your user base (enterprise users may prefer no hard stops – they’d rather pay overages than have service interruption, whereas small self-serve users might prefer a safeguard to not accidentally spend too much). Also, consider monthly maximums or custom plans: If some customers have strict budgets, you could offer a plan where they pre-pay for a certain token pack and never exceed it (service might suspend if they hit the cap, until next month). This is essentially a prepaid model and is similar to the credit system. The downside is if they hit the cap and need service, they experience a cutoff. Decide if you’ll allow rollover of unused tokens to the next month (often, no for simplicity – credits reset each period, encouraging consistent subscription usage, though this means some users will “lose” unused tokens). The fairness and simplicity of your token policy will affect user sentiment. As Stripe’s guidance on token models notes, if allotments are too strict (use-or-lose), customers might feel frustrated by wasted tokens or by running out too fast
stripe.com
stripe.com
. A balanced approach (maybe small rollover or just clearly communicating “ununsed tokens do not carry over”) can manage expectations. Real-World Examples & Insights: We’ve already cited the Hypernian example (a fictitious Stripe scenario) as a model SaaS plan. In the real world, we see various strategies. Many companies simply mark up the API cost and charge usage accordingly. For instance, a service might charge $0.10 per 1,000 tokens on an API that costs them $0.08 per 1,000 – ensuring profit on each call. Twilio’s success with usage-based pricing (pay-per-SMS, etc.) shows that if the value metric is clear, customers will accept it and it can scale revenue nicely
